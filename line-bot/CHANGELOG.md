# 黑絲小蜜 開發紀錄

程式碼本體：`code.gs`（整份貼進 Apps Script 編輯器使用）

---

## 基礎架構
- LINE Bot（Messaging API）+ Google Apps Script（doPost webhook）
- Gemini（結構化解析：名片OCR、行程日期解析）+ Mistral（閒聊、法規比對、摘要）雙模型分工
- 六把金鑰：`_RAW_LINE_TOKEN`、`_RAW_ADMIN_USER_ID`、`_RAW_GEMINI_KEY`、`_RAW_SHEET_ID`、`_RAW_MISTRAL_KEY`、`_RAW_CWA_KEY`（+ 後來加的 `_RAW_DRIVE_FOLDER_ID`）
- Admin User ID 用「首次留空→機器人自己回傳」的方式取得，避免陌生人濫用

## 核心功能（依序建立）
1. **名片辨識**：Gemini Vision 讀圖 → 結構化JSON → 確認 → 寫入 CRM Sheet
2. **行事曆管理**：新增／查詢／刪除／清空，皆走「AI解析＋真人確認」流程，不會不經確認就動日曆
3. **秘書人設閒聊**：Mistral 生成回覆，帶「撩人幹話」人設
4. **天氣查詢**：中央氣象署官方 API，零 AI 介入
5. **法規查詢**：Mistral 比對法規名稱 → Cloudflare Worker 代理抓 MOJ 官網真實條文
6. **三層記憶**：人設（固定）＋長期記憶（Google Sheet，永久）＋短期對話（Cache，30分鐘）
7. **新聞摘要**：RSS 直接抓，零 AI 介入
8. **YouTube／網頁摘要**：抓真實逐字稿/網頁文字餵給 Mistral 摘要，不是憑空生成

## 重大 Bug 修正
| 問題 | 原因 | 修法 |
|---|---|---|
| 生圖功能對口語講法沒反應（例如「生出一張你穿黑絲襪的圖給我」） | 觸發判斷寫死成「必須用『畫』或『生圖』開頭」，這句話開頭是「生出」，對不到就掉進閒聊 | 加一個口語意圖判斷（畫/生成/生出 + 圖/圖片/照片，不限位置），對到就把整句話直接當生圖描述丟進去，不用硬性開頭指令 |
| 打「第3則網址」查新聞連結掉進閒聊，AI編出一堆奇怪內容 | 中文鍵盤打數字有時會自動變成全形（３），JS的`\d`只認半形數字，全形對不到任何靠數字判斷的規則（第幾則網址、刪除第幾筆行程、法規選號…全部受影響），直接漏接掉進閒聊 | 收到文字訊息時統一把全形數字轉成半形再進行後續判斷，一次修掉所有靠數字比對的功能 |
| 國字數字（第三則網址、刪除第三筆）打不通 | 這些觸發規則本來就只認阿拉伯數字，沒設計國字判斷 | 新增 `chineseNumToArabic()`，純規則轉換一~九十九（零AI），套用到「第X則網址」「刪除第N筆行程」「法規總表選號」「已選定法規時的第X條」這四個地方，阿拉伯數字跟國字都能用 |
| 法規情境反查對「法律」講法沒反應（例如「用哪一條法律告他」） | 觸發規則只認「法條」「法規」兩個詞，使用者講「法律」對不到，掉進閒聊被打哈哈帶過 | 觸發規則的關鍵字加入「法律」，跟「法規」「法條」並列 |
| 行程查詢被誤導去閒聊亂編 | `queryPattern` regex 只認「有什麼行程」，漏了「哪些」等講法 | 改成「開頭是日期+內文含行程相關字」的寬鬆判斷 |
| ISO編號「45001/14001」被誤判成日期 | `scheduleKeywords` 的 `\d/\d` 沒有邊界限制 | 加上 `(?<!\d)...(?!\d)` 負向环視 |
| 圖片/文字辨識出空白行程還是跳確認框 | Gemini 解析失敗時沒驗證結果是否為空 | 新增 `title`／`date` 是否有值的檢查 |
| Nominatim（GPS反查）、Supabase 都連不上 | GAS 的 `UrlFetchApp` 無法自訂 User-Agent（Google已知限制），這兩個服務都要求識別身分才放行 | 改走 Cloudflare Worker 中轉（Worker 可自訂 header） |
| 法規單條查詢永遠查無資料 | `LawSingle.aspx` 頁面的 `</div>` 收尾層數跟 `LawAll.aspx` 不同，原本的 regex 是對著全文頁面的層數寫的 | 改用起訖字串定位（`law-article`~`clearfix`），不依賴固定收尾層數 |
| 天氣查詢間歇性失敗 | 部署時 `_RAW_CWA_KEY` 那行常數整個消失（貼上時漏掉開頭） | 補回常數；順便加 try/catch 避免整包壞掉 |
| 生圖／名片辨識／行程解析全部一起失效 | Gemini 免費方案每日20次請求上限用完 | 開通 Google AI Studio 計費（Prepay方案儲值），確認額度連到正確的 GCP 專案 |
| 每隔幾天機器人完全沒回應、執行記錄空白 | Google OAuth「測試中」應用程式的 refresh token 固定7天過期，過期後背景觸發直接失效、連錯誤紀錄都不會留 | 手動重新授權（暫時解法）；正式發布需要 Google 驗證審核（因為用到 Calendar/Sheets/Drive 屬於敏感權限），評估後決定先接受每週手動驗證 |
| 跨日行程（例如12/21~12/22）只存到單一天 | 原本的 JSON schema 只有 `date` 一個欄位，沒有結束日期概念 | 新增 `endDate` 欄位，日期不同就存成跨日／全天活動 |
| 「刑法第三條」這種用中文數字寫條號的查詢，掉進閒聊被瞎編 | 觸發判斷 `第\s*\d+\s*條` 的 `\d+` 只認阿拉伯數字，中文數字「三」比對不到 | regex 加入中文數字字元類別；同時要求 Mistral 把抓到的中文數字條號轉成阿拉伯數字再輸出，因為查詢 MOJ 用的是阿拉伯數字 |
| 沒明講「法規/法條」的法律情境問句（例如「有人偷登入我電腦可以告什麼罪」）掉進閒聊，AI自己編出具體法條號碼（這次剛好編對，但屬於巧合） | 觸發判斷只認「法規/法條/哪個」這類明確字眼，沒涵蓋「違法/犯法/什麼罪/可以告」這種自然講法 | regex 加入這類常見情境詞；另外在人設規則明講「絕對不能自己講出具體條號，一律要打哈哈帶過並請使用者講清楚讓真正的查詢功能處理」，雙重防護 |
| 閒聊到後來會把「小蜜」講成一個獨立於自己之外會偷零食亂跑的寵物角色，甚至否認「我又不是小蜜」 | 短期對話記憶把某次隨口編的哏當事實延續，越滾越大，最後連自己的身分都能講錯（跟先前「英文課」那次是同一種機制，這次撞到更根本的自我認知問題） | 人設規則明講「小蜜」就是自己的名字、不是另一個角色，不要編第三人稱的小蜜故事情節 |

## 功能擴充
- **GPS定位天氣**：LINE位置訊息 → Cloudflare Worker 反查縣市 → 氣象署查詢
- **生圖**：Gemini 生圖 → 上傳存進 Cloudflare Workers KV → 回傳網址給 LINE 顯示
- **法規清單擴充**：常用清單從44筆擴充到63筆（新增民法/刑法/勞工相關法規），另建1024筆完整索引供「情境反查」（例如「有人恐嚇我可以用哪條」），反查結果會附加「AI推測，請自行核對」提醒
- **圖片閒聊**：傳一般照片（非名片非行程）時，改用秘書人設自然回應照片內容，不再只回制式訊息
- **名片照片備份**：辨識完的名片原始照片存進指定 Google Drive 資料夾，CRM Sheet 多一欄連結
- **新聞只列標題**：預設只顯示標題，需要連結另外用「第X則網址」查詢
- **溫度分層設定**：結構化解析（名片/行程/法規比對）統一調低到 0.0~0.2 求準確；閒聊調到 0.55 保留活潑度
- **獨立日曆**（曾經加入、後來revert）：評估後發現使用情境下沒有實際幫助（所有行程都經由bot管理，沒有跟私人行程混在一起的問題），已改回使用預設日曆

## 晨報＋名片總表／備註（2026-09-06）
- **晨報（主動推播，非使用者觸發）**：早上8:30推播「汐止區天氣＋新北市天氣示警（有才顯示）＋今天行程＋股市新聞」，下午2:00另外推播AI新聞。用GAS時間觸發器排程，第一次要在Apps Script編輯器手動執行一次 `setupDailyTriggers()` 才會生效（之後就是全自動，不用再管）
- 汐止區天氣用新北市專屬的鄉鎮區級預報（`F-D0047-071`），跟原本縣市級的 `getWeather()`（`F-C0032-001`）是不同資料集、不同JSON結構，另外寫了 `getHsizhiWeather()`；天氣示警用 `W-C0033-001`（`getNewTaipeiAlert()`）。第一版解析邏輯是照官方文件猜的，部署後第一次觸發真的失敗了——實測發現這組資料集用 PascalCase 欄位（`Locations`/`Location`/`WeatherElement`/`Time`/`ElementValue`），且 `locationName` 參數不會真的過濾（回傳新北市全部29區），已經照實測結果改成正確解析、從陣列裡自己找汐止區。示警那組（`getNewTaipeiAlert`）已實測，外層結構（`records.location[0].hazardConditions.hazards`）跟原本寫的一致，猜對了；測試當下新北市剛好沒有生效中的示警（`hazards: []`），晨報沒顯示這段是正常行為不是bug。唯一不確定的是單筆示警物件裡 `phenomena`/`significance` 有沒有再包一層 `info`，因為沒遇到真正的示警可以驗證，改成兩種結構都吃得下
- 晨報開頭語改成「老爺早安」貼合人設稱呼；汐止天氣原本列3個時段，改成列2個時段（早上8:30查詢時，今天白天06:00~18:00其實已經在進行中，氣象署這組資料不會給已經開始的時段，所以第一筆一定是「今晚」，第二筆是「明天白天」，這是資料源本身的限制，不是抓漏了）
- 晨報改用LINE **Push API**（`pushMessage`），跟其他功能用的Reply API不同，Push會計入LINE的月推播額度——先前評估過「不用做額度查詢」是因為當時全部功能都只用Reply，現在有晨報+下午新聞兩則主動推播，額度使用量還是遠低於免費額度上限，但如果之後再加更多推播功能要重新評估
- **名片總表**：零AI，直接列出CRM表所有聯絡人的公司/姓名/電話
- **名片備註**：CRM表新增「備註」欄，指令「名片備註 關鍵字 備註內容」可以幫既有聯絡人補一句說明（例如「這是做會議室出租的」），`searchContact` 查詢時也會一併比對備註內容。這是為了解決「忘記公司名/人名，但記得業務內容」這種查詢情境——但只對「有補備註」的聯絡人有效，舊名片如果沒補備註還是查不到，這不是bug，是因為資料庫裡本來就沒有這個線索，AI也不會因此瞎猜一個聯絡人出來

## 法規查詢重新設計（2026-09-06）
之前查法規／反查都靠「猜關鍵字regex」當大門，猜不中就直接漏接掉進閒聊（例如講「法律」對不到「法規/法條」關鍵字），改成雙軌並行：
- **總表瀏覽（新增，零AI、不會誤判）**：「法規總表」列出63部常用法規供選號 → 回數字選定（`current_law` 存 pcode，10分鐘有效）→「法規內容」看章節目錄（純讀官方條文資料）→「第X條」直接抓該條全文，全程不用AI猜是哪部法規，選了就是選了
- **情境反查（既有，AI推測，保留當備用管道）**：不知道該查哪部法規、用自然語言描述情境時（例如「照片被亂PO到網路可以告什麼」）才會用到，AI從1024筆完整索引挑相關法規；原本只給1個猜測結果，容易漏掉橫跨多法規的情境（例如肖像權可能同時牽涉民法、個資法），改成最多列3個候選，每個都附「AI推測，請自行核對」提醒
- 兩條路徑共用同一個 `formatLawResult` 去抓取並格式化條文，避免重複程式碼

## 功能擴充（續）
- **法規主題查詢**：問「某部法規的法條有哪些」「XX怎麼規定」這種問句（例如「勞基法有關於加班的法條有哪些」），會抓該法規全文、讓 AI 從真實條文裡挑出相關條號列出來，不是憑空回答。觸發詞刻意鎖定「法條/條款+有哪些/有什麼」「相關規定」「怎麼規定」這種明確問句框架，避免單純聊到「加班」之類主題詞就被誤導去查法規；代價是像「勞基法加班條款」這種沒有問句字尾的詞組不會觸發（會安全落回閒聊，不會亂編，只是不會主動查）
- **法律問句防幻覺雙重防護**：路由層擴大關鍵字（違法/犯法/觸法/什麼罪/可以告/算不算合法），把更多自然講法導去真查詢；人設規則明講「絕對不能自己講出具體條號」，就算漏接也不會讓閒聊層編法條號碼
- **小蜜自我認同修正**：人設明講「小蜜」就是機器人自己的名字，不是另一個角色，修正閒聊層曾經把「小蜜」講成獨立於自己之外的寵物角色、甚至否認自己是小蜜的情況

- **全面改用 Gemini，移除 Mistral 依賴（2026-09-06）**：閒聊持續回「我這邊有點恍神」，用除錯訊息揪出真正原因是 Mistral API 回 429（`Rate limit exceeded`），推測是免費方案的頻率限制。因為 Gemini 那把 key 已經儲值開通付費額度，決定整個 bot 統一用同一把 key：新增 `callGeminiJSON`（沿用 Gemini `responseMimeType: application/json`），`callGeminiText` 補上可調 temperature 參數；`chatWithPersona`、`queryLawTopic`、`queryLaw`、`summarizeYouTube`、`summarizeWebpage` 全部改呼叫 Gemini，移除 `callMistralText`／`_RAW_MISTRAL_KEY`，整份程式碼不再依賴 Mistral。取捨：所有功能集中在同一把 key，若 Gemini 之後撞到自己的額度/頻率限制會一次全掛，不像分兩把 key 時只有單一功能受影響；接受這個風險，額度不夠再回頭改
- 補上一則過去沒涵蓋到的幻覺類型：AI 曾編造「某餐廳打電話來問訂位」這種**根本沒發生過的聯絡事件**，已在人設規則明講不能編造這類事件
